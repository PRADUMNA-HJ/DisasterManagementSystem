# Disaster Management System

## Project Overview

A comprehensive Disaster Management System designed to facilitate coordination and response during emergency situations. The system empowers citizens to report disasters, allows volunteers to register, enables rescue teams to manage field operations, and provides government officials and administrators with tools to monitor incidents and manage the system effectively.

## Objectives

- Provide a structured approach to disaster reporting and management.
- Ensure seamless communication between citizens, volunteers, and rescue teams.
- Create an enterprise-grade backend architecture following Layered MVC patterns.
- Prepare the foundation for a future migration to a Microservices architecture.

## Technology Stack

- **Backend**: Java, Spring Boot, Spring MVC, Spring Security, JWT, Spring Data JPA, Hibernate, JDBC
- **Frontend**: React (Separate Application)
- **Database**: MySQL
- **DevOps**: Docker, Maven, Git, AWS

## High-Level Architecture

The project follows a standard Layered MVC Architecture for clear separation of concerns, scalability, and maintainability.

### MVC Architecture Diagram

```text
Browser
   ↓

   ↓

   ↓
```

*(Note: The request flows downwards as depicted, and the response follows the reverse direction upwards.)*

## Folder Structure

The project is divided into distinct, purpose-driven directories:

- `backend/`: Contains the monolithic Spring Boot application (`disaster-api`), including the `payload/` package for strictly structuring request and response DTOs.
- `frontend/`: Contains the React application (`disaster-web`).
- `database/`: SQL scripts, schemas, mock data, and database design documentation.
- `docker/`: Dockerfiles and docker-compose configurations for containerization.
- `docs/`: Comprehensive project documentation, architectural decisions, and learning notes.
- `env/`: Environment configuration placeholders (dev, test, prod).
- `logs/`: Runtime log files generated by the backend.
- `postman/`: API testing collections and environments.
- `roadmap/`: Detailed step-by-step learning progression files.
- `scripts/`: Utility scripts for automation.
- `screenshots/`: Visual assets of the application interface.
- `.github/`: CI/CD workflows and GitHub templates.

## Microservice Migration Plan

The system is designed as a modular monolith to facilitate a future migration to Microservices. Service interfaces are strictly decoupled from controllers, and bounded contexts are maintained within the package structure. See `docs/Architecture/FutureMicroserviceMigration.md` for the detailed transitional strategy.
